# AppSheetアプリを“ひとりの便利ツール”から“チームの業務システム”にする ── 複数人で使いはじめると出てくる5つの壁と、自作の限界の見極め

「自分ひとりで使っていたときは、何の問題もなかった」
「3人で使いはじめた途端に、データが食い違う・見せたくない情報が見えている・確定したはずの伝票が書き換わっている」。

前回は、アプリに貯まったデータを **ダッシュボードやPDF帳票でどう見せるか** という話を書きました。
今回はその **次の話** です。見せ方が整うと、アプリを見る人・触る人が増えます。
そして人が増えた瞬間から、それまで存在しなかった種類の困りごとが出てきます。

先に大事なことを書いておきます。**これらの壁が出るのは、失敗ではありません。**
アプリが「自分専用の便利ツール」から「**チームの業務システム**」に変わりはじめた証拠です。
この記事では、5つの壁それぞれについて **まず自分でどこまで対処できるか** を示したうえで、
**限界に近づいたときのサイン** と **相談の目安** を中立的に整理します。

> 本記事の例は、よくある **業務効率化** のパターンを伝えるための **一般的な想定例** です。
> 特定の顧客の実績値や機密情報ではありません。環境やデータ構造により結果は変わります。

## Before:ひとりで使っていたときは起きなかったこと

- **見せたくない情報が、全員に見えている**:原価・取引条件・他部署の案件まで同じ画面に並んでいる
- **データが食い違う**:誰かが古い画面のまま入力し、あとから上書きされて数字が合わない
- **確定したものが後から変わる**:締めたはずの伝票が、翌日に書き換えられている
- **承認の記録が残らない**:「承認しました」がチャットや口頭で飛び交い、あとから誰がいつ判断したか追えない
- **直すたびに現場が止まる**:改善しようとアプリを触ると、使っている人の作業に影響が出る

これは「AppSheetが弱い」のでも「メンバーの使い方が悪い」のでもありません。
**ひとり用の作りのまま、人数だけが増えた** という構造が原因です。
**脱Excel** で共有ファイルの取り合いから抜け出した先に、必ず出てくる次の課題だと考えてください。

## 途中:AppSheetなら、ここまでは自分で対処できる

**ノーコード開発** の範囲でも、5つの壁の入口はかなりのところまで自分で塞げます。

- **権限(見せ分け)**:役割ごとに見える範囲・触れる範囲を切り分ける。
  「全員が全部見られる」状態をやめるだけで、事故の多くは減ります
  → 当サイトの **多ユーザーで安全に使うための記事** が参考になります
- **データ同期**:同期は「壊れている」のではなく「**いつ最新になるか**」を決める問題です。
  現場のスマホがオフラインになる前提なのか、常時つながる前提なのかで設計が変わります
  → **データが同期しない場合の対処記事** をご覧ください
- **編集・削除の制限**:ステータスが「確定」「承認済み」になった行は編集も削除もできないようにする。
  ルールを人の記憶ではなくアプリ側に持たせます
  → **ステータスに応じて編集・削除を制限する記事** が具体的です
- **承認フロー**:申請 → 承認 → 記録、程度の流れであれば、設定の範囲で組めます。
  誰がいつ承認したかがデータとして残るだけでも、運用は大きく変わります
  → **承認アプリの記事** が入口になります
- **データ量**:プランごとに扱えるデータの規模には上限があります。
  「無料のままどこまでいけるか」が気になりはじめたら、それは**業務で本当に使われている証拠**です
  → **無料プランのデータ量に関する記事** を確認のうえ、最新の条件は公式情報でご確認ください

データの元になる「現場での記録」側は、**在庫管理アプリの記事** や **写真入力・スキャナーの記事** が前段にあたります。
見せ方は前回の **ダッシュボード/PDF帳票の記事** をご覧ください。

## ひとりで使う場合 / チームで使う場合

| 観点 | ひとりで使う | チームで使う |
|---|---|---|
| 見える範囲 | 全部見えて問題ない | 役割ごとに切り分ける必要がある |
| 入力ミス | 自分で気づいて直せる | 誰が直したか分からなくなる |
| データの鮮度 | ほぼ常に最新 | 同期のタイミング設計が必要 |
| 確定・締め | 自分の頭の中のルール | アプリ側で編集を止める仕組みが必要 |
| 承認 | 不要 | 誰がいつ承認したかの記録が要る |
| 改修 | いつ直してもいい | 使っている人を止めずに直す必要がある |

「チームで使う」列こそが、**業務システムに求められる要件** です。
人数が増えたのに要件が「ひとり用」のままだと、壁として表面化します。

## After:自分で続ける / プロに相談する ── 限界の見極め基準

どちらが良い・悪いではありません。**今の規模と目的に合っているか** で切り分けます。

**まだ自分で続けてよいサイン**

- 見せ分けが「担当者と管理者」程度のシンプルな切り分けで足りている
- 同期のタイミングを決めれば、データの食い違いが実際に減った
- 承認が1段階で、業務ルールが例外なく回っている
- データ量に余裕があり、動作が遅くなっていない
- アプリを直しても、現場の作業が止まらない

**プロに相談したほうが早いサイン**

- **権限の切り分けが細かくなり、表示速度との両立が難しくなってきた**(見せ分けと性能は同時に効いてきます)
- **同期の不整合が、設定の調整では収まらない**(多くの場合は使い方ではなく **データ構造の設計** が原因です)
- **承認が多段階・条件分岐つきになった**(金額や部署で経路が変わる等。業務ルールの実装は要件定義が必要です)
- **データ量が増えて動作が重い / プランの上限が見えてきた**(課金と設計を同時に判断する場面です)
- **使いながら安全に改修したい**(現場を止めずに直す運用は、テストと変更管理の設計が要ります)

このうち **権限とデータ構造** は、後から足そうとすると作り直しになりやすい部分です。
「あとで整えよう」と画面側で吸収し続けるより、**壁が見えた時点で設計から相談したほうが結果的に速く・安く済む** ことは少なくありません。
相談・発注の受け皿としては **AppSheet制作・保守サービスの記事** もご覧ください。

## まとめ:人数が増えたら、要件も変わっている

**ひとり用のアプリと、チームの業務システムは、必要な設計が違います。**
うまくいっているアプリほど使う人が増え、増えたぶんだけ新しい要件が出てきます。
それは順調に進んでいるということです。

まずは5つの壁のうち、いま実際に困っているものを **1つだけ** 選んでください。
たいていは「見せたくない情報が見えている(権限)」か「データが食い違う(同期)」のどちらかです。
そこから手をつけるのが、いちばん効果が分かりやすいはずです。

そのうえで、権限と速度の両立・同期の不整合・多段階の承認・データ量・止めずに直す改修 ──
このあたりに壁のサインが出てきたら、それは「次の設計」への合図かもしれません。

自分で直せる範囲か、設計から見直したほうがよいか ── 迷ったら、まずご相談ください。
いま何人で使っていて、どこで困っているかをうかがい、切り分けから一緒に整理します。
